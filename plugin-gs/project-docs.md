# 프로젝트 문서 규격

이 플러그인의 에이전트들이 **대상 레포 안에서** 읽는 문서 두 장의 규격이다. 스킬·에이전트 본문에는 골격을 두지 않고 여기를 참조한다 — 골격이 여러 군데 흩어지면 문서마다 항목이 어긋난다.

| 문서 | 경로 (대상 레포 기준) | 읽는 쪽 | 없으면 채우는 곳 |
| --- | --- | --- | --- |
| 프로젝트 정체 | `docs/project-identity.md` | `gs:planner` | `/gs:idea` §0-4 |
| 아키텍처 | `docs/architecture.md` | `gs:frontend-dev` · `gs:backend-dev` | `/gs:implement-loop` §0-7 |

## 왜 레포 안인가

노션이나 OS 레포에 모아두면 대상 코드와 떨어져 드리프트가 난다. 스택을 바꾸는 커밋과 문서를 고치는 커밋이 같은 PR에 들어가야 문서가 거짓말을 하지 않는다. 에이전트는 이미 레포 경로를 인자로 받으므로 찾는 비용도 없다.

## docs/project-identity.md — 기획의 바닥

`gs:planner`가 기획서 초안을 쓰기 전에 읽는다. **"이 아이디어를 이 프로젝트가 해야 하는가"** 를 판단할 근거다. 이게 없으면 planner는 아이디어만 보고 기획하므로, 방향이 다른 기능이 그럴듯하게 들어온다.

### 골격 — 정체

여섯 항목. 제목을 그 이름 그대로 쓴다 — planner가 제목으로 섹션을 찾는다.

| 항목 | 내용 |
| --- | --- |
| 정체 | 이 프로젝트는 무엇인가. 한 문장. "~하는 서비스" 형태 |
| 페르소나 | 1순위 사용자 한 명. 나이·직업 나열이 아니라 **어떤 상황에서 무엇이 아쉬운 사람인지**. 만든 사람 본인이면 그렇게 적는다 |
| 톤·태도 | 제품이 사용자에게 말 거는 방식. UI 카피와 기능 결정의 기준이 된다 |
| 방향성 | 6~12개월 뒤 어디까지 가려는가. 지금 없는 것을 적어도 된다 |
| 하지 않을 것 | 방향성의 반대편. **비워두지 않는다** — 비어 있으면 기획이 아무 데로나 뻗는다 |
| 제약 | 혼자 만드는 사람의 시간·비용·기술 제약. 유료 API를 못 쓴다거나 주말에만 만든다거나 |

### 인터뷰 질문 — 정체

문서가 없을 때 `/gs:idea`가 `AskUserQuestion`으로 **한 건씩** 묻는다. 항목당 하나, 최대 여섯 번.

1. 이 프로젝트를 한 문장으로 하면? → `정체`
2. 이걸 제일 먼저 쓸 사람은 누구고, 그 사람은 지금 어떤 상황에서 아쉬운가? → `페르소나`
3. 사용자에게 어떤 태도로 말 걸고 싶은가? (담백하게 / 친근하게 / 전문가처럼 …) → `톤·태도`
4. 반년~1년 뒤 이 프로젝트가 어디까지 가 있으면 만족스러운가? → `방향성`
5. 반대로, 사람들이 원해도 안 할 것은? → `하지 않을 것`
6. 시간·비용·기술에서 못 넘는 선이 있나? → `제약`

답이 짧으면 그대로 적는다. 살을 붙이지 않는다 — 이 문서는 사람의 판단을 기록하는 자리지 AI가 상상하는 자리가 아니다.

## docs/architecture.md — 구현의 바닥

`gs:frontend-dev`·`gs:backend-dev`가 첫 코드를 쓰기 전에 읽는다. 각 에이전트는 **`## 공통` + 자기 섹션만** 읽는다.

FE·BE를 한 파일에 두는 이유: 개인 프로젝트는 대개 풀스택 단일 레포라 경계가 얕고, 두 파일로 나누면 API 계약 같은 걸친 내용이 양쪽에 중복돼 어긋난다.

### 골격 — 아키텍처

세 섹션. 제목을 그 이름 그대로 쓴다.

```markdown
## 공통
| 항목 | 내용 |
| 런타임·언어 | Node 22 / TypeScript |
| 패키지 매니저 | pnpm |
| 폴더 구조 | 라우팅·비라우팅 폴더 규칙, 전역 공통 위치 |
| 실행 | 개발 서버·타입체크·빌드 명령 |
| 배포 | 어디에 어떻게 올라가는가 |
| 환경 변수 | 이름과 용도만. **값은 적지 않는다** |

## 프론트엔드
| 항목 | 내용 |
| 프레임워크 | Next.js App Router 등 |
| 상태 관리 | 서버 상태·클라이언트 상태 각각 무엇으로 |
| 스타일링 | Tailwind / CSS Modules / … + 디자인 토큰 위치 |
| 데이터 패칭 | API 호출 계층이 어디 있고 어떤 규약인가 |
| 컴포넌트 규칙 | 공통 컴포넌트 위치, 분리 기준 |

## 백엔드
| 항목 | 내용 |
| 서버 형태 | Next.js Route Handler / 별도 서버 / 서버리스 |
| DB·ORM | 무엇을 쓰고 스키마 파일이 어디 있는가 |
| API 규약 | 경로 네이밍, 응답 형태, 에러 응답 형태 |
| 인증 | 방식과 세션 저장 위치 |
| 외부 연동 | 쓰는 외부 API와 그 경계 |
```

**해당 없는 섹션은 지운다.** 백엔드가 없는 프로젝트에 빈 `## 백엔드`를 남기면, backend-dev가 "적혀 있지 않다"와 "없다"를 구분하지 못한다. 지웠으면 `## 공통`에 한 줄 남긴다: `백엔드 없음 — 클라이언트 전용`.

### 인터뷰 질문 — 아키텍처

문서가 없을 때 `/gs:implement-loop`가 묻는다. 다만 **레포에서 읽어낼 수 있는 것은 묻지 않는다.** `package.json`·설정 파일·기존 폴더 구조로 채울 수 있는 항목(런타임·패키지 매니저·프레임워크·스타일링·ORM·실행 명령)은 먼저 읽어서 초안에 채우고, 사람에게는 **읽어낸 초안을 보여주며 확인**만 받는다.

읽어서 알 수 없어 반드시 물어야 하는 것:

1. 상태 관리를 서버/클라이언트 각각 무엇으로 가져갈 것인가 (기존 코드에 없을 때)
2. API 응답·에러 응답의 형태를 어떻게 통일할 것인가
3. 인증이 필요한가, 필요하면 어떤 방식인가
4. 배포는 어디로 가는가

신규 프로젝트(스캐폴딩 전)면 읽을 코드가 없으므로 전부 묻는다. 이때는 스캐폴딩 계획이 곧 이 문서의 초안이다.

## 갱신 규칙

- **두 문서 다 사람 승인 없이 쓰지 않는다.** 초안은 AI, 확정은 사람 — 파이프라인 전체와 같은 원칙이다.
- 에이전트는 이 문서들을 **읽기만 한다.** 구현 중 스택이 문서와 달라졌으면 고치지 말고 보고에 한 줄 남긴다. 문서를 고치는 건 스킬(사람 승인 경유) 몫이다.
- 문서와 코드가 어긋나면 **코드가 맞다.** 에이전트는 코드를 따르고 그 사실을 보고한다.
- 문서가 있어도 내용이 비었거나 `TBD`뿐이면 없는 것으로 친다.
