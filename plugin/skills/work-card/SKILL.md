# /os:work-card — 슬랙 URL → 팀 카드 → 개인 작업 페이지 → 설계 초안

작업의 **출발점**을 세 곳에 맞춘다. 팀 카드(팀이 보는 상태), 개인 페이지(내가 쓰는 상황 공유), 설계서 초안(사람이 확정할 것).

## 두 개의 노션, 두 개의 MCP

| 대상 | 워크스페이스 | 쓰는 MCP | 접근 |
|---|---|---|---|
| 팀 작업 카드 · 스레드 모음 | cashwalkteam | `claude.ai Notion` (`notion-fetch`, `notion-query-data-sources`) | **읽기 전용** |
| 개인 업무 로그 | guesung | `notion-home` (`API-post-page`, `API-patch-page`, `API-query-data-source`, `API-patch-block-children`) | 읽기·쓰기 |

개인 DB는 `claude.ai Notion`으로 접근하면 404가 난다. 반대로 팀 DB는 `notion-home`에 없다. 섞어 쓰지 않는다.

| 식별자 | 값 |
|---|---|
| 팀 작업리스트 data source | `collection://d7229a7c-7fd6-4547-b321-b5370660d0f1` |
| 팀 스레드 모음 data source | `collection://1f2a054b-7d82-80bf-af60-000b25972a74` |
| 팀 작업리스트에서 "나" | `user://341d872b-594c-81a0-b4c2-0002f0e8c323` |
| 개인 업무 로그 database | `5f408e05-0015-4532-bcd8-bd36439bec5a` |
| 개인 업무 로그 data source | `8412989c-11e3-4685-8af9-35299fc6c097` |

## ① 팀 카드 찾기

슬랙 URL에서 `p<숫자>` 메시지 ID를 뽑는다. URL 형식이 달라도(스레드 파라미터 유무 등) 이 ID는 같다.

1. **스레드 모음에서 찾기.** URL 속성 이름이 `URLhttps://…`로 시작하는 기형 이름이라 SQL에서 그대로 인용한다.
   ```sql
   SELECT url, "", "작업카드", "태그"
   FROM "collection://1f2a054b-7d82-80bf-af60-000b25972a74"
   WHERE "URLhttps://w1748334471-0ys520938.slack.com/archives/C08TWHCQF2T/p1778133587298739" LIKE '%p<메시지ID>%'
   ```
   `작업카드`가 비어 있지 않으면 그 페이지가 팀 카드다. `notion-fetch`로 `할일`·`상태`·`작업 ID`·`QA 체크리스트`·`메모`를 읽는다.
2. **없으면 작업리스트에서 대조.** 담당자가 나이고 미완료인 카드를 뽑아, 슬랙 스레드 첫 메시지의 제목·키워드와 `할일`을 대조한다. 확실한 것 하나만 후보로 낸다. 애매하면 후보를 내지 않는다.
   ```sql
   SELECT url, "할일", "상태", "작업 ID", "메모"
   FROM "collection://d7229a7c-7fd6-4547-b321-b5370660d0f1"
   WHERE "담당자" LIKE '%341d872b-594c-81a0-b4c2-0002f0e8c323%' AND "상태" NOT IN ('완료', '보관함')
   ```
3. **그래도 없으면 사람에게 묻는다.** `AskUserQuestion`으로 "팀 카드를 만들까요?" — 만들면 `할일`(스레드 제목 기반 제안)·`담당자`=나·`상태`=진행 예정·`관련 스레드/문서`를 채운다. **사용자가 고르기 전에는 만들지 않는다.** 팀 카드는 팀 전체에 보이는 경계다.

찾은(또는 만든) 팀 카드 URL·`작업 ID`·`할일`을 기억한다. 이후 단계와 implement-loop가 쓴다.

## ② 개인 작업 페이지

1. **중복 확인.** 이 DB에는 `스레드 URL` 속성이 없다. **슬랙 URL은 `이름`(title)의 하이퍼링크로 들어간다** — 이게 이 DB의 실제 운영 방식이다. `API-query-data-source`로 최근 페이지를 훑어 `이름` rich_text의 `text.link.url`에서 `p<메시지ID>`를 뽑아 대조한다. 있으면 그 페이지를 재사용하고 ③으로 간다.
2. **생성** (`API-post-page`, parent = data source `8412989c-11e3-4685-8af9-35299fc6c097`):

   | 속성 | 값 |
   |---|---|
   | `이름` | 팀 카드 `할일` 그대로. 팀 카드가 없으면 스레드 제목. **전체에 슬랙 URL을 link로 건다** |
   | `프로젝트` | §프로젝트 판정 참조 |
   | `상태` | `진행 중` |
   | `작업 시작 날짜` | 오늘 |
   | `메모 / 일정` | `팀 카드 #<작업 ID> <팀 카드 URL>` |

### 프로젝트 판정

작업 대상 레포의 경로로 `프로젝트`(select)를 정한다. 경로를 모르면 비워 둔다 — 틀린 값을 넣는 것보다 낫다.

| 레포 경로 | `프로젝트` |
|---|---|
| `레포지토리/cashwalk/**` (CashwalkHome, CashwalkHomepageAstroWeb, CashwalkTownlifeCommunityMainWeb, CashwalkTownWalkWeb 등 전부) | `넛지헬스케어` |
| `레포지토리/guesung/web-memo` | `웹 메모` |
| `레포지토리/guesung/**` 그 외 | 이름이 일치하는 옵션이 있으면 그것, 없으면 **비워 둔다** |

선택 가능한 옵션은 `웹 메모` · `우아한테크코스` · `우아한테크코스 프리코스` · `봄봄` · `넛지헬스케어` 뿐이다. **없는 옵션을 새로 만들지 않는다.**

3. **본문 골격** (`API-patch-block-children`). 제목은 이 다섯 개를 이 이름 그대로 쓴다 — implement-loop가 제목으로 섹션을 찾는다.

   ```
   ## 설계서
   ## TDL
   ## QA 체크리스트
   ## 논의 필요
   ## 해결한 문제
   ## 루프 로그
   ```

## ③ 설계 초안

슬랙 스레드를 읽는다 (`slack_read_thread`). 스레드에 기획서·피그마 링크가 있으면 링크만 기록하고 내용을 추측하지 않는다.

`## 설계서`에 아래 순서로 초안을 쓴다. **초안이다. 확정은 사람이 한다.**

1. 한 줄 목표 — 스레드가 요청한 것
2. 변경 범위 — 어느 화면·어느 컴포넌트·어느 API. 모르는 건 "확인 필요"로
3. 동작 명세 — 입력·상태·분기. 스레드에 없는 건 쓰지 않는다
4. 범위 밖 — 이번에 안 하는 것

`## 논의 필요`에 **"이대로 만들면 막힐 지점"**을 쓴다. 각 항목은 `무엇이 불명확한가 → 어느 선택지가 있는가 → 내가 추천하는 쪽과 이유`. 스레드에서 답이 안 나오는 것만 적는다. 이 섹션이 비어 있어야 implement-loop가 시작되므로, 여기 적는 것은 곧 "사람이 답해야 루프가 돈다"는 뜻이다.

`## TDL`·`## QA 체크리스트`·`## 해결한 문제`·`## 루프 로그`는 설계서가 확정된 뒤 implement-loop가 채운다. 지금은 비워 둔다.

## 마지막 출력

세 줄. 그 이상 쓰지 않는다.

```
팀 카드: #<작업 ID> <할일> — <URL>   (또는 "없음 · 생성 안 함")
개인 페이지: <URL>
논의 필요: n건
```

그리고 **`AskUserQuestion`으로 다음 단계를 묻는다.** 사용자가 `/os:implement-loop`을 직접 치게 두지 않는다 — 설계서를 방금 만든 이 자리가 "이대로 진행할지" 판단하기 가장 좋은 시점이다.

- `논의 필요`가 **0건**이면: "설계서 확정하고 구현 루프를 시작할까요?" → 승인하면 `/os:implement-loop <개인 페이지 URL>`을 이어서 실행한다.
- `논의 필요`가 **1건 이상**이면: 루프는 어차피 시작하지 못한다(implement-loop §0-3). 대신 **첫 항목부터 하나씩 묻는다.** 답을 받을 때마다 `## 설계서`에 반영하고 해당 항목을 `## 논의 필요`에서 지운다. 전부 비면 위의 시작 질문으로 넘어간다.
- 사용자가 "나중에"를 고르면 페이지 URL만 남기고 끝낸다. 재개는 `/os:work-card` 같은 URL로 다시 부르거나 `/os:implement-loop <페이지 URL>`로 한다.

**묻기 전에 페이지 저장을 끝낸다.** 사용자가 어떤 답을 하든 여기까지의 결과는 노션에 남아 있어야 한다.

## 하지 않는 것

- 팀 카드의 속성을 바꾸지 않는다 (생성 시 초기값 제외). 상태 변경은 사람이 한다.
- 설계서에 스레드에 없는 동작을 지어내지 않는다. 빈 곳은 `논의 필요`로.
- 개인 페이지를 슬랙 URL 하나당 하나 넘게 만들지 않는다.

## 왜 이렇게 나눴나

- **팀 카드 읽기 전용** — 팀 카드는 팀이 보는 상태판이다. AI가 임의로 상태를 바꾸면 팀이 잘못된 신호를 받는다. 상황 공유는 개인 페이지에 쌓고, 팀 카드에 옮길지는 사람이 정한다.
- **스레드 URL을 키로** — 작업 하나 = 슬랙 스레드 하나라는 팀 관행이 이미 있다. 그 키로 팀 카드·개인 페이지를 묶으면 세 곳이 어긋나지 않는다. 개인 DB에는 전용 속성이 없어 `이름`의 링크에 싣는다. 속성을 늘리는 대신 이미 굴러가던 방식을 따랐다 — DB는 사람이 매일 보는 것이고, OS 편의로 열을 늘리면 사람 쪽이 불편해진다.
- **설계 초안을 여기에** — OS.md 3절의 "AI 설계 초안 · 막힐 지점 지적"이 이 단계다. 설계 권한은 사람에게 있고, AI는 사람이 검토할 재료를 만든다.
- **다음 단계를 사람이 치게 두지 않는 이유** — `논의 필요`를 방금 만든 자리가 그것을 답하기 가장 싼 시점이다. 여기서 끝내고 사람이 나중에 페이지를 다시 열면, 스레드 맥락을 처음부터 다시 읽어야 한다. 물어보는 것은 자동화를 줄이는 게 아니라, **사람의 판단을 가장 값싼 시점으로 당기는 것**이다.
