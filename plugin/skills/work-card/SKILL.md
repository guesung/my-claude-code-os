# /os:work-card — 슬랙 URL → 팀 카드 → 개인 작업 페이지 → 설계서 씨앗

작업의 **출발점**을 세 곳에 맞춘다. 팀 카드(팀이 보는 상태), 개인 페이지(내가 쓰는 상황 공유), 설계서 씨앗(`/os:design`이 이어받을 것).

```
/os:work-card       팀 카드 · 개인 페이지 · 씨앗(한 줄 목표 · 막힐 지점 초벌)
      │
      ▼
/os:design          레포 탐색 → AS-IS/TO-BE · 변경 지점 · 다이어그램 → 확정 도장
      │
      ▼
/os:implement-loop  구현 → 검사 → 리뷰 → QA → 테섭 배포 → PR
```

## 노션 접근

**시작 전에 [notion-databases.md](../../notion-databases.md)를 읽는다.** 이 스킬이 쓰는 네 식별자 — 팀 작업리스트 · 팀 스레드 모음 · 담당자 "나" · 개인 업무 로그 data source — 와 속성 규칙이 전부 거기 있다.

이 스킬은 **두 노션을 모두** 만진다. 팀은 `claude.ai Notion`으로 읽기만, 개인은 `notion-home`으로 읽고 쓴다. 섞어 쓰면 404다.

## ① 팀 카드 찾기

슬랙 URL에서 `p<숫자>` 메시지 ID를 뽑는다. URL 형식이 달라도(스레드 파라미터 유무 등) 이 ID는 같다.

1. **스레드 모음에서 찾기.** URL 속성 이름이 `URLhttps://…`로 시작하는 기형 이름이라 SQL에서 그대로 인용한다.
   ```sql
   SELECT url, "", "작업카드", "태그"
   FROM "<팀 스레드 모음 data source>"
   WHERE "<URL 속성 이름>" LIKE '%p<메시지ID>%'
   ```
   data source URI와 **기형인 URL 속성 이름 전체**는 [notion-databases.md](../../notion-databases.md#팀-스레드-모음)에 있다. 이름을 줄여 쓰면 조회가 실패한다.
   `작업카드`가 비어 있지 않으면 그 페이지가 팀 카드다. `notion-fetch`로 `할일`·`상태`·`작업 ID`·`QA 체크리스트`·`메모`를 읽는다.
2. **없으면 작업리스트에서 대조.** 담당자가 나이고 미완료인 카드를 뽑아, 슬랙 스레드 첫 메시지의 제목·키워드와 `할일`을 대조한다. 확실한 것 하나만 후보로 낸다. 애매하면 후보를 내지 않는다.
   ```sql
   SELECT url, "할일", "상태", "작업 ID", "메모"
   FROM "<팀 작업리스트 data source>"
   WHERE "담당자" LIKE '%<담당자 "나" UUID>%' AND "상태" NOT IN ('완료', '보관함')
   ```
3. **그래도 없으면 사람에게 묻는다.** `AskUserQuestion`으로 "팀 카드를 만들까요?" — 만들면 `할일`(스레드 제목 기반 제안)·`담당자`=나·`상태`=진행 예정·`관련 스레드/문서`를 채운다. **사용자가 고르기 전에는 만들지 않는다.** 팀 카드는 팀 전체에 보이는 경계다.

찾은(또는 만든) 팀 카드 URL·`작업 ID`·`할일`을 기억한다. 이후 단계와 design·implement-loop가 쓴다. **`작업 ID`는 숫자만 저장돼 있고**(예: `1389`), implement-loop ⑧이 PR 제목 접두사 `[CK-1389]`를 만들 때 쓴다.

## ② 개인 작업 페이지

1. **중복 확인.** 슬랙 URL은 `이름`(title)의 하이퍼링크로 들어간다 — 전용 속성이 없다([왜 그런지](../../notion-databases.md#개인-업무-로그)). `API-query-data-source`로 최근 페이지를 훑어 `이름` rich_text의 `text.link.url`에서 `p<메시지ID>`를 뽑아 대조한다. 있으면 그 페이지를 재사용하고 ③으로 간다.
2. **생성** (`API-post-page`, parent = 개인 업무 로그 data source). 채울 속성은 `이름`·`프로젝트`·`상태`·`작업 시작 날짜`·`메모 / 일정` 다섯이다. 각 칸의 값과 `프로젝트` select 판정은 [notion-databases.md](../../notion-databases.md#개인-업무-로그)를 그대로 따른다.
3. **본문 골격** (`API-patch-block-children`). [notion-databases.md의 본문 섹션 골격](../../notion-databases.md#본문-섹션-골격) 여섯 제목을 그 이름 그대로 만든다 — design·implement-loop가 제목으로 섹션을 찾는다.

## ③ 설계서 씨앗

슬랙 스레드를 읽는다 (`slack_read_thread`). 스레드에 기획서·피그마 링크가 있으면 링크만 기록하고 내용을 추측하지 않는다.

**여기서는 씨앗까지만 만든다.** 본격 설계서(AS-IS·TO-BE·변경 지점·동작 명세·다이어그램)는 **`/os:design`** 이 레포를 열어 채운다. 이 스킬은 슬랙과 노션만 보므로 "어느 컴포넌트·어느 API"를 알 방법이 없다.

`## 설계서`에 두 가지만 쓴다.

1. **한 줄 목표** — 스레드가 요청한 것
2. **범위 밖** — 스레드가 명시적으로 제외한 것. 없으면 생략한다(추측해서 채우지 않는다)

`## 논의 필요`에 **"이대로 만들면 막힐 지점"**의 초벌을 쓴다. 각 항목은 `무엇이 불명확한가 → 어느 선택지가 있는가 → 내가 추천하는 쪽과 이유`. **스레드만 읽고도 명백히 빈 것**만 적는다 — 레포를 봐야 알 수 있는 것은 `/os:design`이 ④에서 추가한다.

`## TDL`·`## QA 체크리스트`·`## 해결한 문제`·`## 루프 로그`는 설계서가 확정된 뒤 implement-loop가 채운다. 지금은 비워 둔다.

## 마지막 출력

세 줄. 그 이상 쓰지 않는다.

```
팀 카드: #<작업 ID> <할일> — <URL>   (또는 "없음 · 생성 안 함")
개인 페이지: <URL>
막힐 지점 초벌: n건
```

그리고 **`AskUserQuestion`으로 다음 단계를 묻는다.** 사용자가 `/os:design`을 직접 치게 두지 않는다 — 스레드를 방금 읽은 이 자리가 설계로 넘어가기 가장 싼 시점이다. 여기서 끊으면 나중에 스레드 맥락을 처음부터 다시 읽어야 한다.

- `설계 시작` → **`/os:design <개인 페이지 URL>`** 을 이어서 실행한다. 막힐 지점은 design ⑤가 레포를 본 뒤 한꺼번에 묻는 것이 낫다 — 지금 물으면 레포를 안 본 채로 답하게 되고, design이 같은 걸 또 묻는다.
- `나중에` → 페이지 URL만 남기고 끝낸다. 재개는 `/os:design <페이지 URL>`로 한다.

**`/os:implement-loop`을 여기서 부르지 않는다.** 설계서가 아직 씨앗이라 루프가 시작하지 못한다(implement-loop §0-3의 확정 도장 확인).

**묻기 전에 페이지 저장을 끝낸다.** 사용자가 어떤 답을 하든 여기까지의 결과는 노션에 남아 있어야 한다.

## 하지 않는 것

- 팀 카드의 속성을 바꾸지 않는다 (생성 시 초기값 제외). 상태 변경은 사람이 한다.
- 설계서에 스레드에 없는 동작을 지어내지 않는다. 빈 곳은 `논의 필요`로.
- 개인 페이지를 슬랙 URL 하나당 하나 넘게 만들지 않는다.

## 왜 이렇게 나눴나

- **팀 카드 읽기 전용** — 팀 카드는 팀이 보는 상태판이다. AI가 임의로 상태를 바꾸면 팀이 잘못된 신호를 받는다. 상황 공유는 개인 페이지에 쌓고, 팀 카드에 옮길지는 사람이 정한다.
- **스레드 URL을 키로** — 작업 하나 = 슬랙 스레드 하나라는 팀 관행이 이미 있다. 그 키로 팀 카드·개인 페이지를 묶으면 세 곳이 어긋나지 않는다. 개인 DB에는 전용 속성이 없어 `이름`의 링크에 싣는다. 속성을 늘리는 대신 이미 굴러가던 방식을 따랐다 — DB는 사람이 매일 보는 것이고, OS 편의로 열을 늘리면 사람 쪽이 불편해진다.
- **씨앗까지만 여기서** — OS.md 3절의 "AI 설계 초안 · 막힐 지점 지적"은 이 스킬과 `/os:design`이 나눠 맡는다. 이 스킬은 슬랙과 노션만 보고, design은 레포를 연다. **필요한 입력이 다르므로 재실행 단위도 다르다** — 설계가 틀렸을 때 work-card를 다시 부르면 노션 페이지 셋업까지 다시 하는 일이 된다.
- **다음 단계를 사람이 치게 두지 않는 이유** — 스레드를 방금 읽은 자리가 설계로 넘어가기 가장 싼 시점이다. 여기서 끝내고 사람이 나중에 페이지를 다시 열면, 스레드 맥락을 처음부터 다시 읽어야 한다. 다만 **막힐 지점을 여기서 묻지는 않는다** — 레포를 안 본 채로 답하게 되고, `/os:design`이 같은 걸 또 묻게 된다. 묻는 것은 가장 싼 시점으로 당기되, **답할 재료가 갖춰진 뒤**여야 한다.
