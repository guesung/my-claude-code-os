# /os:self-qa — QA 명세 작성 → 자동 판정 → 수동 안내

"전부 자동화"가 목표가 아니다. **자동으로 판정할 수 있는 것과 없는 것의 경계를 명시적으로 남기는 것**이 목표다.
"자동화 못 하니 검증 안 함"이 되는 항목이 하나도 없어야 한다.

## 저장소 — 노션 "QA 항목" DB (guesung, `notion-home` MCP)

| 식별자 | 값 |
|---|---|
| 페이지 "QA 체크리스트" (📜 문서 DB 안) | `3ca89de0-2fde-816b-8352-cfbb0fdc28c2` |
| 인라인 DB "QA 항목" database | `67c9937c-44f1-4d43-b306-d6fd66031cac` |
| 인라인 DB "QA 항목" data source | `bf2d9b85-98bb-4d4f-9ec4-d6a2018ff02f` |
| `작업` relation 대상 = 업무 로그 data source | `35e89de0-2fde-8010-ae3b-000b081dad99` |

행 하나 = QA 항목 하나. 모든 작업의 항목이 이 DB 한 곳에 쌓이고 `작업` relation으로 구분된다. 작업별 페이지를 따로 만들지 않는다 — 4주차에 "수동 비율"·"FAIL 잦은 유형"을 세려면 한 곳에 있어야 한다.

| 속성 | 타입 | 채우는 규칙 |
|---|---|---|
| `항목` | title | "X하면 Y가 보인다" — 관측 가능한 문장 하나 |
| `작업` | relation | 개인 업무 로그 페이지 |
| `ID` | text | `Q-01`, `Q-02` … 작업 안 순번 |
| `유형` | select | `자동` / `수동` |
| `상태` | select | `미실행` → `PASS` / `FAIL` / `수동 대기` → (사람이) `수동 확인` |
| `전제` | text | 경로 · 로그인/데이터 상태 · 뷰포트(web/webview) |
| `판정 기준` | text | 무엇을 보고 PASS라 하는가. DOM·텍스트·네트워크·스크린샷 중 하나로 |
| `재현 방법` | text | 수동만. `진입 → 조작 → 기대 결과 → 확인 포인트` |
| `수동 사유` | text | 수동만. 왜 브라우저로 못 보는가 |
| `증거` | url | 스크린샷·PR 링크 |
| `회차` | number | 실행된 루프 회차 |
| `실행일` | date | |

로컬 설계서 파일로 호출됐을 때(개발·검증용)는 DB 대신 설계서 파일 하단 `## QA 체크리스트`에 같은 컬럼의 표로 쓴다.

## 모드

| 인자 | 하는 것 | 호출처 |
|---|---|---|
| `--checklist-only` | ① 명세 작성 → ④ DB에 행 생성 (`상태`=미실행) | implement-loop §0-3 |
| `--run` | DB에서 이 작업의 행을 읽어 ② 자동 실행 → ③ 수동 안내 → ④ 갱신 | implement-loop ⑥ |
| 없음 | 전부 | 사람이 직접 |

## ① 명세 작성

입력은 개인 페이지의 `## 설계서`(동작 명세·변경 범위·범위 밖). 설계서에 없는 동작은 항목으로 만들지 않는다.

규칙:

1. **동작 명세 한 줄당 항목 ≥ 1.** 명세 줄을 인용해 어느 줄에서 나왔는지 `전제`에 남긴다.
2. **경계 항목 필수.** 아래 넷은 해당 화면에 그 상태가 존재하면 반드시 항목으로 만든다.
   - 데이터 없음 (빈 목록·0건)
   - 요청 실패 (API 에러·타임아웃)
   - 로딩 중 (스켈레톤·스피너)
   - 권한/상태 분기 (비로그인·미인증·조건 미충족)
3. **문장은 관측 가능하게.** "정상 동작한다" ✗ → "목록이 비어 있으면 `아직 등록된 항목이 없어요` 문구가 보인다" ✓
4. **`확인 필요`·`TBD` 금지.** 설계서에서 못 정하면 항목을 만들지 말고 implement-loop가 `## 논의 필요`로 보내게 한다.

**자동/수동 판정 기준** (고정):

| 자동 | 수동 |
|---|---|
| 브라우저에서 DOM·텍스트·스크린샷·콘솔·네트워크로 관측 가능 | 실기기 센서(걸음수·위치), 푸시, 결제, 앱 브릿지 네이티브 동작, 외부 서비스 실제 연동, 특정 계정 상태(등급·이력) |

**애매하면 수동.** "자동"이라 해놓고 못 돌린 항목은 검증 안 된 채 통과된다. 수동으로 두면 최소한 사람이 본다.

## ② 자동 실행

`유형`=자동 항목을 **한 번에 묶어** `/guesung:ui-verify`에 넘긴다. 항목마다 `ID`·`항목`·`전제`·`판정 기준`을 스펙으로 준다. ui-verify는 항목별 PASS/FAIL과 증거(스크린샷 경로·DOM 상태·콘솔)를 돌려준다.

- ui-verify가 항목을 "관측 불가"로 돌려주면 그 항목은 **`유형`을 수동으로 바꾸고** ③으로 보낸다. 자동 판정에 실패한 항목을 PASS로 두지 않는다.
- dev 서버가 안 뜨거나 라우트를 못 찾으면 멈춘다. 그건 QA 실패가 아니라 실행 환경 문제라 implement-loop 정지 조건 D에 준한다.

## ③ 수동 안내

`유형`=수동 항목마다 `재현 방법`을 쓴다. 형식 고정:

```
진입: <URL 또는 화면 경로> (<전제 상태>)
조작: <1> → <2> → <3>
기대: <무엇이 보여야/일어나야 하는가>
확인: <어디를 보면 판정할 수 있는가>
```

`상태`=`수동 대기`. 사람이 확인하면 `수동 확인`으로 바꾼다 — 스킬은 이 상태를 만들지 않는다.

## ④ DB 갱신

- `--checklist-only`: 이 작업(`작업` relation)의 기존 행이 있으면 **지우지 않고** ID가 같은 행을 갱신, 새 ID만 추가한다. 이전 회차 결과를 잃지 않기 위해서다.
- `--run`: `상태`·`증거`·`회차`·`실행일`을 갱신. FAIL은 `증거`에 실패 증거를 넣는다.
- 개인 페이지 `## QA 체크리스트` 섹션에는 **DB 링크 + 요약 한 줄**만 남긴다: `PASS n · FAIL n · 수동 대기 n → <QA 항목 DB URL>`. 데이터는 DB 한 곳에만 둔다.

## 출력

사람용 표 + 기계용 JSON. implement-loop가 JSON을 읽는다.

```
| ID | 유형 | 상태 | 항목 |
|---|---|---|---|
| Q-01 | 자동 | PASS | … |
| Q-04 | 수동 | 수동 대기 | … |
```

```json
{ "pass": 5, "fail": 1, "manual": 2, "fail_items": [ { "id": "Q-03", "item": "…", "evidence": "…" } ] }
```

마지막 한 줄: `자동 n건 중 PASS n · FAIL n, 수동 n건 재현 방법 기록.` 총평 없음.

## 하지 않는 것

- FAIL 항목을 고치지 않는다. 판정까지가 책임이다. 수정은 implement-loop ⑥이 한다.
- 설계서에 없는 동작을 항목으로 지어내지 않는다.
- 수동 항목을 `수동 확인`으로 바꾸지 않는다. 그건 사람이 실제로 본 뒤에만.
- 팀 작업 카드의 `QA 체크리스트` URL 속성을 건드리지 않는다. 팀에 공유할지는 사람이 정한다.

## 왜 이렇게 나눴나

- **명세와 실행을 분리** — 명세는 설계서가 확정되는 순간 나올 수 있고, 실행은 코드가 있어야 한다. 합치면 "구현 다 되고 나서 QA 항목을 생각"하게 되고, 그때는 구현에 맞춰 항목이 왜곡된다.
- **애매하면 수동** — 자동 판정의 거짓 PASS가 수동의 비용보다 비싸다.
- **DB 한 곳** — 항목별 이력이 쌓여야 "이 유형은 매번 FAIL"이 보인다. 원장과 같은 논리다.
