# /os:implement-loop — 구현 오케스트레이터

한 번 호출하면 아래를 **끝까지** 돈다. 중간에 사용자에게 묻지 않는다. 멈추는 조건은 §정지 조건에만 있다.

```
슬랙 URL ─→ /os:work-card ─→ 개인 작업 페이지 (설계서 초안 · 논의 필요)
                                    │
[사람] 설계서 확정 · 논의 필요 비우기 ◄┘
   │
   ▼
① 구현
② 검사기        /os:ledger-check --json               ─┐
③ 리뷰어        Agent: os:ledger-reviewer               │ 회차 ≤ MAX_ROUNDS
④ 리팩토링      (a) FAIL 수정  (b) FF 개선 제안         │ 종료: ② FAIL 0 · ③ FAIL 0 · ⑤ 반려 없음
⑤ 반려자        Agent: os:rejector                     ─┘
⑥ 셀프 QA       /guesung:ui-verify
⑦ Draft PR      /guesung:pr
   │
   ▼
[사람] 최종 검토
```

## 0. 시작 전 확인

1. **인자 파싱.** `$ARGUMENTS`의 첫 토큰으로 분기한다.
   - `slack.com/archives/…` → 슬랙 URL. **`/os:work-card`를 먼저 실행**해 개인 작업 페이지를 만들고(또는 찾고), 그 페이지 URL로 이어간다. work-card가 `논의 필요`를 채웠다면 거기서 멈춘다(정지 조건 B).
   - `notion.com/…` → 개인 업무 로그 페이지 URL. 팀 카드 URL을 주면 안 된다 — 팀 카드는 읽기 전용이고 OS 섹션이 없다.
   - 그 외 → 로컬 설계서 파일 경로(개발·검증용).
   - 없으면 멈추고 인자를 요구한다.
2. **작업 페이지 읽기.** 개인 페이지는 **`notion-home` MCP**로 읽는다(`API-retrieve-page-markdown`). `## 설계서`·`## TDL`·`## QA 체크리스트`·`## 논의 필요`·`## 루프 로그` 제목으로 섹션을 찾는다. 로컬 파일이면 파일 전체를 설계서로 삼고 TDL·QA는 설계서에서 직접 뽑는다.
3. **설계서 확정 여부.** `## 논의 필요`가 비어 있지 않거나 설계서에 `TBD`/`미정`/`확인 필요`가 있으면 **시작하지 않는다.** 미확정 항목을 나열하고 멈춘다. 설계가 흔들리는 상태에서 루프를 돌리면 회차만 태운다.
   - `## TDL`이 비어 있으면 설계서에서 뽑아 채운다(작업 단위 = 커밋 단위). `## QA 체크리스트`가 비어 있으면 설계서의 동작 명세에서 항목을 뽑고 각 항목에 `자동`/`수동` 표시를 단다. 둘 다 사람 확인 없이 채운다 — 설계서가 확정됐으면 거기서 도출되는 것이라 판단 여지가 없다.
4. **전역 스킬 확인.** `/os:ledger-check`를 `--diff /dev/null`로 한 번 실행한다. 종료 코드 2면 전역 스킬 누락이므로 멈춘다.
5. **상태 파일 초기화.** 대상 레포의 `.omc/state/implement-loop.json`:
   ```json
   { "card": "<URL 또는 경로>", "branch": "<작업 브랜치>", "round": 0, "max_rounds": 3, "rounds": [] }
   ```
   같은 페이지로 이미 상태 파일이 있고 `round > 0`이면 **이어서** 돈다(재개). 새로 시작하려면 사용자가 상태 파일을 지운다.

## ① 구현

- 브랜치는 `/guesung:spec-build`의 브랜치 규칙을 따른다(`feature/<기획명>` base → `feature/<기획명>-<작업명>` 작업 브랜치).
- TDL 순서대로 구현한다. spec-build의 "한 작업마다 사용자 확인" 단계는 **이 루프에서는 생략한다** — 그 확인을 ②~⑤가 대신한다.
- TDL 항목을 끝낼 때마다 커밋한다. 커밋 단위가 곧 나중에 사람이 되짚을 단위다.
- 구현 중 설계서로 판단이 안 되는 지점이 나오면 **멈추지 말고** 가장 보수적인 선택을 하고, 페이지의 `## 논의 필요`에 "무엇을 어떻게 가정했는지"를 적는다. 최종 검토에서 사람이 본다.
- TDL 항목을 끝낼 때마다 페이지 속성 `완료 작업`에 그 항목을, `TODO`에 남은 항목을 갱신한다(`API-patch-page`). 사람이 목록 뷰에서 진행률을 보는 용도다.

## ②~⑤ 루프

`round`를 1 올리고 아래를 순서대로 실행한다. 각 단계의 결과를 `rounds[]`에 쌓는다.

### ② 검사기

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/skills/ledger-check/scripts/ledger_check.py" --json
```

`fail_count`와 `verdicts`를 기록한다.

### ③ 리뷰어

`Agent` 도구로 `os:ledger-reviewer`를 띄운다. 프롬프트에는 **아래 셋만** 넣는다. 설계서나 구현 과정의 대화는 넣지 않는다.

```
diff: --base <base 브랜치>
ledger: ${CLAUDE_PLUGIN_ROOT}/ledger/ledger.yaml
checker: <② JSON 그대로>
```

결과 JSON의 `fail_count`·`warn_count`·`verdicts`를 기록한다.

### ④ 리팩토링

**(a) 위반 수정 — 필수.** ②와 ③의 FAIL 항목을 전부 고친다. 항목마다 커밋 하나. 커밋 메시지에 원장 id를 넣는다(`fix: L-101 …`). WARN은 고치지 않고 페이지 `## 논의 필요`에 옮긴다.

**(b) FF 기준 개선 제안 — 선택.** `/guesung:advance-code`가 존재하면 실행해 제안 목록을 받는다. 존재하지 않으면 `rounds[].advance_code = "skipped: not installed"`로 기록하고 넘어간다. 제안은 **적용하지 않는다.** 페이지 `## 루프 로그`에 "현재 → 제안 → 근거" 형태로 남겨 최종 검토에서 사람이 고른다.

(a)에서 고친 게 하나도 없고 (b) 제안도 없으면 ⑤로 간다. 고친 게 있으면 ⑤로 간다 — 고친 코드도 반려자가 봐야 한다.

### ⑤ 반려자

`Agent` 도구로 `os:rejector`를 띄운다. 프롬프트에는 **diff 지시 하나만** 넣는다.

```
diff: --base <base 브랜치>
```

결과 JSON의 `rejected`·`reasons`·`intent_confidence`를 기록한다.

- `rejected: true` → 각 reason을 고치고(항목마다 커밋, 메시지에 `reject:` 접두사) **회차를 올리지 않고** ②로 돌아간다. 반려 근거 수정은 같은 회차 안의 재검사다.
  - 단, 같은 회차에서 반려가 **2번** 나오면 회차를 올린다. 무한 재검사를 막는다.
- `intent_confidence: low` → 반려 근거가 없어도 페이지 `## 논의 필요`에 "의도가 읽히지 않음 + 반려자가 지목한 부분"을 적는다. 가독성 신호다.
- 반려자 reason이 ②③의 FAIL과 같은 파일:라인을 가리키면 **하나로 합쳐** 기록한다. 관점이 다를 뿐 같은 결함이다.

### 종료 판정

아래를 **모두** 만족하면 루프를 나간다.

- ② `fail_count == 0`
- ③ `fail_count == 0` (WARN은 허용)
- ⑤ `rejected == false`

만족하지 못하고 `round == max_rounds`면 **정지 조건 A**다.

## ⑥ 셀프 QA

`--skip-qa`가 없으면 `/guesung:ui-verify`를 페이지의 `## QA 체크리스트`로 실행한다.

- 항목별 PASS/FAIL을 `qa`에 기록한다.
- FAIL 항목은 고치고 **②부터 한 회차를 더 돈다**(회차 상한은 그대로 적용). QA에서 고친 코드도 원장·반려자를 거쳐야 한다.
- ui-verify가 "자동 불가"로 표시한 항목은 **재현 방법**을 페이지 `## QA 체크리스트`의 해당 항목 옆에 적는다. 수동 QA는 사람 몫이다. "자동화 못 하니 검증 안 함"이 되지 않게 경계를 남기는 것이 요점이다.

## ⑦ Draft PR

`/guesung:pr`로 Draft PR을 만든다. PR 본문 `검증` 섹션에 아래를 넣는다.

- 원장 검사 최종 결과 (② 표)
- 루프 회차 수, 회차별 FAIL 수 추이 (예: `3 → 1 → 0`)
- 반려자 최종 판정과 의도 확신도
- QA PASS/FAIL 수, 수동 QA 항목 수
- FF 개선 제안 수 (사람이 고를 것)

## 마무리 — 개인 작업 페이지 갱신

개인 페이지면 `notion-home` MCP(`API-patch-page`, `API-patch-block-children`)로:

- `## TDL` 전부 체크. 속성 `완료 작업`에 전체, `TODO`는 비움
- `## 루프 로그`에 회차별 요약 (검사기 FAIL → 리뷰어 FAIL → 반려 여부, 한 줄씩)
- `## 논의 필요`에 루프 중 쌓인 항목 (가정한 것, WARN, 의도 불명확 지점, FF 제안)
- 속성 `메모 / 일정`에 PR URL 추가, `상태`를 `정리 필요`로 (사람의 최종 검토 대기라는 뜻)
- 속성 `대기 작업`에 수동 QA 항목 수·논의 필요 건수

**팀 작업 카드는 건드리지 않는다.** 상태를 `QA 대기`로 올릴지, PR을 연결할지는 사람이 최종 검토에서 정한다. 마지막 출력에 "팀 카드 #<작업 ID> 갱신 필요: 상태 → QA 대기, PR 연결"을 한 줄 넣어 잊지 않게만 한다.

로컬 설계서면 같은 내용을 설계서 파일 하단에 `## 루프 로그` 섹션으로 붙인다.

마지막 출력은 한 문단: PR URL, 회차 수, 남은 사람 몫(수동 QA n건, 논의 필요 m건, FF 제안 k건). 그 이상의 총평은 쓰지 않는다.

## 정지 조건

루프를 멈추고 사람에게 넘기는 경우. 멈출 때는 **어디서 왜 멈췄는지**와 상태 파일 경로를 남긴다. 재개는 같은 인자로 다시 호출하면 된다.

| | 조건 | 남기는 것 |
|---|---|---|
| A | `max_rounds`를 다 썼는데 종료 판정 미달 | 남은 FAIL 목록, 회차별 추이. **같은 항목이 3회 연속 FAIL이면 원장 항목 자체가 모호한 것**일 수 있으니 그 id를 짚는다 |
| B | 설계서 미확정 (§0-3) | 미확정 항목 |
| C | 전역 스킬 누락 (§0-4) | 누락 스킬 이름 |
| D | 빌드·타입체크 실패가 ④에서 2회 연속 | 에러 로그 |
| E | 노션 페이지 접근 실패 (개인 DB는 `notion-home`, 팀 DB는 `claude.ai Notion` — MCP를 바꿔 썼는지 먼저 확인) | URL, 에러 |

## 하지 않는 것

- 설계서를 바꾸지 않는다. 설계가 틀렸다고 판단되면 `논의 필요`에 적고 설계서대로 구현한다.
- 원장(`ledger.yaml`)을 고치지 않는다. 원장 갱신은 사람의 최종 검토 → `/guesung:review-feedback-log` → 승격 경로로만 일어난다.
- 루프 도중 사용자에게 묻지 않는다. 물어야 할 것은 전부 `## 논의 필요`로 미룬다.
- 팀 작업 카드를 쓰지 않는다. 읽기만 한다.
- FF 제안을 적용하지 않는다.

## 왜 이렇게 나눴나

- **③과 ⑤를 별도 Agent로 띄우는 이유** — 같은 컨텍스트에서 자기 코드를 검토하면 무조건 통과시킨다. 컨텍스트를 끊는 것이 유일한 방어다.
- **⑤에 diff만 주는 이유** — 설계서를 주면 반려자는 "설계서와 맞는가"만 본다. 설계서 없이 의도가 읽혀야 그 코드는 남이 읽을 수 있는 코드다.
- **반려 수정에 회차를 안 올리는 이유** — 회차는 "원장 기준 수렴"을 세는 단위다. 반려자 지적은 원장 밖 결함이라 같은 회차의 재검사로 친다. 대신 2회 반려 시 회차를 올려 발산을 막는다.
- **④(a)와 (b)를 나누는 이유** — 위반과 취향을 섞으면 원장이 오염된다. (a)만 자동으로 고치고 (b)는 사람이 고른다.
- **루프 중 묻지 않는 이유** — 사람 개입이 "시작·끝"인 것이 3주차의 성공 기준이다. 묻고 싶은 것은 페이지에 쌓아 한 번에 본다.
