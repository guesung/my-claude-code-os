# 노션 DB 카탈로그

이 OS가 읽고 쓰는 노션 DB의 **식별자·속성·접근 규칙의 단일 진실 공급원(SSOT)**이다.
스킬 본문에는 ID를 두지 않는다. 노션을 건드리는 스킬은 **시작 전에 이 파일을 읽고** 필요한 값을 채운다.

ID가 바뀌거나 속성이 늘면 **여기만 고친다.** 스킬 여섯 곳을 찾아다니지 않는다.

## 두 개의 노션, 두 개의 MCP

| 워크스페이스 | 쓰는 MCP | 접근 | 담기는 것 |
|---|---|---|---|
| cashwalkteam (팀) | `claude.ai Notion` — `notion-fetch`, `notion-query-data-sources` | **읽기 전용** | 팀 작업리스트 · 스레드 모음 · 코드 리뷰 문서화 DB |
| guesung (개인) | `notion-home` — `API-post-page`, `API-patch-page`, `API-query-data-source`, `API-patch-block-children`, `API-retrieve-page-markdown`, `API-retrieve-a-page` | 읽기·쓰기 | 업무 로그 · QA 항목 · 문제 해결 일지 |

**개인 DB를 `claude.ai Notion`으로 열면 404다. 반대로 팀 DB는 `notion-home`에 없다.** 섞어 쓰지 않는다.
노션 접근이 실패했을 때 가장 먼저 의심할 것은 권한이 아니라 **MCP를 바꿔 쓴 것**이다.

팀 DB는 `collection://` URI로 SQL을 걸고, 개인 DB는 UUID를 API 인자로 넘긴다. 표기 형태가 다른 이유가 이것이다.

## 팀 작업리스트

팀이 보는 상태판(`1파트 작업리스트`). **AI는 읽기만 한다** — 카드 생성은 `/os:work-card` ①-3에서 사람이 고를 때만.

| 식별자 | 값 |
|---|---|
| data source | `collection://d7229a7c-7fd6-4547-b321-b5370660d0f1` |
| 담당자 = "나" | `user://341d872b-594c-81a0-b4c2-0002f0e8c323` |

쓰는 속성: `할일` · `상태` · `작업 ID` · `담당자` · `QA 체크리스트` · `메모` · `관련 스레드/문서`

- `작업 ID`는 **숫자만** 저장돼 있다(예: `1389`). `CK-`는 PR 제목에서 붙이는 접두사이고 노션 값이 아니다.
- `상태` 중 `완료` · `보관함`은 미완료 조회에서 제외한다.

## 팀 스레드 모음

슬랙 스레드 ↔ 팀 작업 카드를 잇는 DB. 작업 하나 = 슬랙 스레드 하나라는 팀 관행의 실체.

| 식별자 | 값 |
|---|---|
| data source | `collection://1f2a054b-7d82-80bf-af60-000b25972a74` |

쓰는 속성: `작업카드`(relation) · `태그` · URL 속성

> **URL 속성 이름이 기형이다.** 이름 자체가 `URLhttps://w1748334471-0ys520938.slack.com/archives/C08TWHCQF2T/p1778133587298739` 로 시작한다. SQL에서 이 전체를 그대로 인용해야 한다. 짧게 줄이면 조회가 실패한다.

## 코드 리뷰 문서화 DB

리뷰 원장의 **적립층**. 사람이 지적한 것이 여기 쌓이고, `/os:ledger-promote`가 골라 실행층(`plugin/ledger/ledger.yaml`)으로 올린다.

| 식별자 | 값 |
|---|---|
| data source | `collection://3c1a054b-7d82-801a-a2be-000bf6c7cdf3` |

쓰는 속성: `이름` · `내용` · `분류` · `상태`(`적용중`/`폐기`) · `중요도`(`높음`/`보통`/`낮음`) · `적용 범위` · `PR` · `url`

- 이 DB에는 `검증법`·`재발` 필드가 없다. **실행층이 따로 필요한 이유가 이것이다.**
- `url`이 원장 `출처`와 대조하는 키다.
- 채우는 것은 `/guesung:review-feedback-log`의 일이다. `/os:ledger-promote`는 읽기만 한다.

## 개인 업무 로그

OS가 상황을 쌓는 곳. 작업 하나 = 페이지 하나이며, 팀 카드와는 **슬랙 스레드 URL**로 묶인다.

| 식별자 | 값 |
|---|---|
| database | `5f408e05-0015-4532-bcd8-bd36439bec5a` |
| data source | `8412989c-11e3-4685-8af9-35299fc6c097` |

### 속성

`이름` · `프로젝트` · `상태` · `작업 시작 날짜` · `메모 / 일정` · `TODO` · `PR` · `우선순위` · `평가` · `회고` · `블로그 소재` · `Blocking` · `ID`

OS가 채우는 것은 이 중 다섯이다.

| 속성 | 타입 | 채우는 규칙 |
|---|---|---|
| `이름` | title | 팀 카드 `할일` 그대로. 팀 카드가 없으면 스레드 제목. **전체에 슬랙 URL을 link로 건다** |
| `프로젝트` | select | [레포 경로 ↔ 프로젝트](#레포-경로--프로젝트) 참조 |
| `상태` | **status** | 생성 시 `진행 중`. select이 아니라 status 타입이다 — `{"select":{...}}`로 보내면 400 `상태 is expected to be status.` 가 난다 |
| `작업 시작 날짜` | date | 생성일 |
| `메모 / 일정` | rich_text | `팀 카드 #<작업 ID> <팀 카드 URL>` |
| `ID` | unique_id | 노션이 매긴다. **값 자체가 `DB-123` 형태다 — `DB-`를 두 번 붙이지 않는다** |

> **`스레드 URL` 속성은 없다.** 슬랙 URL은 `이름`(title)의 하이퍼링크로 들어가며, 그게 중복 확인 키다. 중복 확인은 `이름` rich_text의 `text.link.url`에서 `p<메시지ID>`를 뽑아 대조한다.
>
> **제목을 고칠 때 링크를 반드시 보존한다.** `rich_text` 배열을 통째로 다시 쓰되 각 조각의 `text.link.url`을 원래 값 그대로 넣는다. 링크 없이 텍스트만 갈아치우면 같은 스레드로 페이지가 하나 더 생긴다.
>
> 설계 확정을 담을 속성이 없다. 확정 도장은 본문 `## 설계서` 안에 둔다.

### 본문 섹션 골격

`/os:work-card` ②-3이 이 여섯 제목을 **이 이름 그대로** 만든다. `/os:design`·`/os:implement-loop`가 제목으로 섹션을 찾으므로 이름을 바꾸면 파이프라인이 끊긴다.

```
## 설계서
## TDL
## QA 체크리스트
## 논의 필요
## 해결한 문제
## 루프 로그
```

`## QA 체크리스트`에는 데이터를 두지 않는다 — [QA 항목](#qa-항목) DB 링크와 요약 한 줄만 남긴다.

## QA 항목

행 하나 = QA 항목 하나. **모든 작업의 항목이 이 DB 한 곳에 쌓이고** `작업` relation으로 구분된다. 작업별 페이지를 따로 만들지 않는다 — "수동 비율"·"FAIL 잦은 유형"을 세려면 한 곳에 있어야 한다.

| 식별자 | 값 |
|---|---|
| 페이지 "QA 항목" (인라인 DB가 놓인 페이지) | `3cb89de0-2fde-8048-bcd2-cc834d7e03f6` |
| 인라인 DB database | `67c9937c-44f1-4d43-b306-d6fd66031cac` |
| 인라인 DB data source | `bf2d9b85-98bb-4d4f-9ec4-d6a2018ff02f` |
| `작업` relation 대상 = 업무 로그 data source | `8412989c-11e3-4685-8af9-35299fc6c097` |

| 속성 | 타입 | 채우는 규칙 |
|---|---|---|
| `항목` | title | "X하면 Y가 보인다" — 관측 가능한 문장 하나 |
| `작업` | relation | 개인 업무 로그 페이지 |
| `ID` | text | `Q-01`, `Q-02` … 작업 안 순번 |
| `유형` | select | `자동` / `수동` |
| `상태` | select | `미실행` → `PASS` / `FAIL` / `수동 대기` → (사람이) `수동 확인` |
| `전제` | text | 경로 · 로그인/데이터 상태 · 뷰포트(web/webview) |
| `판정 기준` | text | 무엇을 보고 PASS라 하는가. DOM·텍스트·네트워크·스크린샷 중 하나로 |
| `재현 방법` | text | 수동만. `진입 → 조작 → 기대 결과 → 확인 포인트` |
| `수동 사유` | text | 수동만. 왜 브라우저로 못 보는가 |
| `증거` | url | 스크린샷·PR 링크 |
| `회차` | number | 실행된 루프 회차 |
| `실행일` | date | |

- `수동 확인` 상태는 **스킬이 만들지 않는다.** 사람만 찍는다.
- 갱신할 때 기존 행을 지우지 않는다. ID가 같으면 갱신, 새 ID만 추가 — 이전 회차 결과를 잃지 않기 위해서다.

## 문제 해결 일지DB

막혔다가 뚫은 문제를 한 행으로. **사람 승인 없이 쓰지 않는다**(`/os:problem-log` ②).

| 식별자 | 값 |
|---|---|
| database | `35189de0-2fde-8085-9688-d281c81eb6b2` |
| data source | `35189de0-2fde-80ec-895d-000bb8b2945f` |

| 속성 | 타입 | 채우는 규칙 |
|---|---|---|
| `이름` | title | **증상** 한 줄. 원인이 아니라 겉으로 드러난 현상 (예: `드롭다운이 열린 상태의 Escape가 메모 상세까지 닫음`) |
| `상황` | rich_text | 무엇이 어떻게 안 됐나. 증상 · 에러 메시지 · 재현 조건. 코드 식별자는 인라인 코드로 |
| `원인` | rich_text | 왜 그랬나 + 확인한 근거. 못 밝혔으면 `미확인 — 우회함` |
| `해결 방법` | rich_text | 무엇을 바꿔서 뚫었나. 커밋 해시나 `파일:라인`. 아직이면 `(아직 해결은 X)`로 시작 |
| `유형` | select | `버그` · `고민` · `궁금증` · `학습` · `상용 배포 이슈` · `힘들게 해결한 버그` · `구현` |
| `프로젝트` | select | **`넛지헬스케어` · `웹 메모` 둘뿐.** [레포 경로 ↔ 프로젝트](#레포-경로--프로젝트) 참조 |
| `날짜` | date | 오늘 |
| `트레이드 오프 / 해결 과정` | rich_text | 다른 선택지가 있었고 그중 골랐을 때만. 없으면 비운다 |
| `메모` | rich_text | 업무 로그 페이지 mention · PR 링크 |

> 기존 행들은 `원인`과 `유형`이 비어 있다. 손으로 쓰다 빠진 칸이다. **이 DB에서 그 두 칸을 채우는 것이 자동화의 값이다** — 원인 없는 일지는 나중에 검색해도 쓸모가 없고, 유형 없는 일지는 "자주 막히는 유형"을 셀 수 없다.

## 레포 경로 ↔ 프로젝트

`프로젝트`(select)는 개인 업무 로그와 문제 해결 일지DB가 함께 쓴다. **선택지가 서로 다르므로** 아래 표를 그 DB의 선택지로 한 번 더 거른다.

| 레포 경로 | `프로젝트` |
|---|---|
| `~/Desktop/레포지토리/cashwalk/**` (CashwalkHome, CashwalkHomepageAstroWeb, CashwalkTownlifeCommunityMainWeb, CashwalkTownWalkWeb 등 전부) | `넛지헬스케어` |
| `~/Desktop/레포지토리/guesung/web-memo` | `웹 메모` |
| `~/Desktop/레포지토리/guesung/**` 그 외 | 이름이 일치하는 옵션이 있으면 그것, 없으면 **비운다** |

| DB | 선택 가능한 옵션 |
|---|---|
| 개인 업무 로그 | `웹 메모` · `우아한테크코스` · `우아한테크코스 프리코스` · `봄봄` · `넛지헬스케어` |
| 문제 해결 일지DB | `넛지헬스케어` · `웹 메모` |

**없는 옵션을 새로 만들지 않는다.** 판정이 안 서면 비워 둔다 — 틀린 값을 넣는 것보다 낫다. 자동화가 select를 늘리기 시작하면 DB가 금방 지저분해진다.

역방향(`프로젝트` → 레포 경로)은 `/os:design` §0-4가 쓴다. `넛지헬스케어`는 레포가 여럿이라 **한 곳으로 정해지지 않는다** — 페이지 제목·설계서 키워드로 후보를 좁히고, 둘 이상이면 사람에게 고르게 한다.

## 왜 한 곳에 모았나

- **ID는 스킬의 지식이 아니라 환경의 사실이다.** 스킬이 여섯 개든 열 개든 `개인 업무 로그 data source`는 하나다. 스킬마다 적어두면 DB를 옮기거나 다시 만들었을 때 어느 스킬이 옛 ID로 남았는지 알 수 없다.
- **`8412989c…`가 세 스킬에 중복돼 있었다** — work-card·design·self-qa. 셋 중 하나만 고치면 나머지 둘이 조용히 틀린 곳을 가리킨다. 그 틀림은 노션이 404를 뱉을 때까지 드러나지 않는다.
- **속성 규칙까지 같이 옮긴 이유** — "`프로젝트`에 없는 옵션을 만들지 않는다"는 problem-log만의 규칙이 아니라 그 DB의 규칙이다. DB 옆에 두면 나중에 그 DB를 쓰는 스킬이 하나 더 생겨도 자동으로 지켜진다.
- **대신 스킬 하나만 읽어서는 ID를 알 수 없다.** 그래서 노션을 건드리는 스킬은 본문 첫머리에 이 파일을 읽으라고 못 박는다. 읽기 한 번을 더 하는 비용으로, 여섯 곳이 어긋날 가능성을 없앤 것이다.
