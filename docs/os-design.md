# 리뷰 지식을 먹고 자라는 구현 OS — 설계 초안

> 4주 동안 만들 나만의 클로드 코드 OS. `ideas.md` 1번(기능 구현 OS)을 축으로 하고,
> **"과거 코드리뷰에서 받은 지적을 자산화해 다음 구현에 먹인다"** 를 차별화 축으로 삼는다.

## 1. 한 줄 정의

설계는 사람이 하고, 구현부터 Draft PR까지는 AI가 한다.
단 AI는 **리뷰 원장(ledger)** 을 기준으로 스스로를 검증하며,
사람에게 지적받은 것은 원장에 적립되어 다음 사이클의 검증 기준이 된다.

## 2. 왜 이 주제인가

강의 온보딩 문서가 제시한 OS의 조건에 비춘 판단.

| 조건 | 이 OS에서 충족되는 방식 |
|---|---|
| 자동 피드백 신호가 있는가 | 타입체크 · 빌드 · 컨벤션 위반 · 스크린샷 · 원장 항목 위반 |
| 사람의 역할이 명확한가 | **설계**와 **최종 승인**만. 그 사이는 AI |
| 주차별로 자동화 수준을 올릴 수 있는가 | 사람 개입 횟수를 5회 → 1회로 줄여가는 궤적이 곧 커리큘럼 |
| 조별 리뷰에서 보여줄 게 나오는가 | 매주 실제 PR 1개 + 재발률 숫자 |

핵심은 온보딩 문서의 질문 **"우리가 가진 지식을 AI에게 어떻게 전달하지?"** 에 정면으로 답한다는 점이다.
컨벤션 문서를 컨텍스트에 붙이는 건 누구나 한다. 이 OS는 **사람이 실제로 지적한 것**을 소스로 삼는다.

## 3. 골격

온보딩 문서의 공통 골격(`의도 공유 → 실행 → 피드백 → ↻`)에 대응시킨 형태.

```
[사람]  설계                                    최종 승인 → PR 공유
          │                                        ↑
          ▼                                        │
[AI]   구현 ──→ 셀프 리뷰 ──→ 수정 ──→ 시각 검증 ──→ Draft PR
                  ↑    (상한 3회)  │
                  └───────↻───────┘
                  │
              [리뷰 원장]  ←── 사람이 새로 지적한 것 적립
```

- **의도 공유** = 설계서 (사람이 작성, AI는 읽기만)
- **실행** = 구현 → 셀프 리뷰 → 수정 루프
- **피드백** = 사람의 최종 검토. 여기서 나온 지적이 원장으로 되돌아감 ← **이 화살표가 이 OS의 정체성**

## 4. 구성 요소

### 4.1 리뷰 원장 (Ledger)

이 OS의 심장. 한 항목 = 한 개의 "다시는 지적받지 않겠다"는 규칙.

```
- id: L-001
  지적: useCallback을 습관적으로 붙임
  출처: PR #482 리뷰 코멘트
  검증법: 변경분에서 useCallback/useMemo 사용처 grep
  재발: 2회
```

- 검증 가능한 형태로 적는 것이 관건. "코드를 깔끔하게"는 원장 항목이 될 수 없다.
- 재발 횟수가 곧 4주차의 채점 지표.

### 4.2 역할 분리

| 역할 | 하는 일 | 왜 분리하나 |
|---|---|---|
| 구현자 | 설계서 → 코드 | |
| 리뷰어 | 원장 + 컨벤션 기준으로 판정 | **자기 코드를 자기가 승인하면 무조건 통과시킨다.** 별도 컨텍스트여야 함 |
| 검증자 | 빌드 · 타입 · 실제 화면 동작 | 코드를 읽는 것과 돌려보는 것은 다른 일 |

### 4.3 재사용할 기존 자산

이미 갖고 있는 스킬들. 새로 만드는 게 아니라 **하나의 루프로 묶는 것**이 이 강의의 과제.

`/convention-review` · `/full-review` · `/pr` · `/ui-verify` · `/self-qa-checklist` · `/review-feedback-log`

## 5. 4주 로드맵

각 주차의 성공 기준은 "사람 개입 횟수가 줄었는가".

| 주차 | 배울 개념 | 얹을 것 | 사람 개입 |
|---|---|---|---|
| 1 | 스킬 · 컨텍스트 | 설계서 → 구현 스킬 1개. 원장 v0 (수기 10항목) | 설계 + 매 단계 호출 |
| 2 | 에이전트 | 구현자 / 리뷰어 분리. 리뷰어는 원장으로만 판정 | 리뷰 결과 승인 |
| 3 | 오케스트레이터 · 루프 | 구현→리뷰→수정 루프 (상한 3회). 시각 검증 결합 | 시작 + 최종 확인 |
| 4 | 하네스 · 평가 | 재발률 채점. Draft PR까지 자동. 실패는 원장에 적립 | 시작만 |

버그 픽스 OS(`ideas.md` 2번)는 폐기하지 않고, 3주차에 **같은 골격을 재사용하는 두 번째 진입점**으로 검토한다.
원장과 리뷰어를 그대로 쓰고 앞단만 "재현"으로 바꾸면 된다.

## 6. 열린 결정 사항

- [ ] 리뷰 원장의 소스를 어디서 가져올 것인가 (GitHub PR 코멘트 / Notion / 수기)
- [ ] 실습 대상 코드베이스를 무엇으로 할 것인가 (실제 업무 레포 / 별도 샘플)
- [ ] 설계서의 형식과 저장 위치
