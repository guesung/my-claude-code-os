### 4주 동안 함께 할 OS 주제

### 직접 작성

1. 기능 구현 OS
   1. 설계 : (인간) 기능 설계 관련하여 논의 (설계는 직접 하기 위해 자동 X) > 설계서를 노션 페이지에 기록
   2. 구현 : 1.1.의 설계 바탕으로 기능 구현 > Draft PR 업로드 > 팀 컨벤션 + 지난 코드 리뷰들 바탕으로 리뷰 > 구현한 기능 및 결과를 시각적으로 공유 > (인간) 검토 > PR 공유
2. 버그 픽스 OS : 이슈 링크/내용을 공유 > 원인/해결 방법/재현 방법 공유 > 재현 환경 구성 > (인간) 재현 > 수정할 것을 명령 > 수정 > 이슈를 노션 페이지에 기록 > 원인/해결 방법 정리해서 슬랙에 초안 작성
3. 문의 답변 OS : 문의 내용 전달 > 코드 기반으로 관련 내용 탐색 > 문의 관련된 내용 > (인간) 컨펌 > 문의 답변을 슬랙에 초안 작성

### 추가 후보 (추천)

판단 기준은 온보딩 문서에서 뽑았다 — ① 자동으로 얻을 수 있는 피드백 신호가 있는가 ② 사람의 개입 지점이 명확한가 ③ 주차별로 자동화 수준을 올릴 수 있는가.
이 중 ①이 없으면 "루프"가 성립하지 않아 3·4주차에 얹을 개념이 사라진다.

4. 스펙 정합 OS : 기획서 PDF + Figma + 슬랙 스레드 투입 > 항목별로 나란히 대조표 생성 > 충돌·누락만 추출 > (인간) 충돌 건별 결정 > 합의된 단일 스펙 확정 > 작업카드에 기록해 재발 방지
   - 신호 : 출처 간 불일치 건수 (자동 검출·카운트 가능)
   - 사람 : 충돌이 났을 때 어느 쪽이 맞는지 결정하는 것만
   - 강점 : 구현이 아니라 **구현 앞단**을 다뤄서 다른 수강생과 겹칠 확률이 가장 낮음. 잘못된 스펙으로 만든 코드는 리뷰를 아무리 잘해도 못 구제한다는 지점을 찌름

5. PR 1차 리뷰어 OS : 남의 PR 링크 투입 > 변경 의도 파악 > 컨벤션·과거 리뷰 원장 기준으로 1차 리뷰 초안 > (인간) 취사선택 후 실제 코멘트 게시 > 내가 실제로 단 코멘트와 AI 초안을 대조해 원장 갱신
   - 신호 : **내가 실제로 단 코멘트와의 일치율** — 이게 그대로 채점 지표가 됨
   - 사람 : 어떤 지적을 실제로 내보낼지 고르는 것만
   - 강점 : 1번 채택안과 리뷰 원장을 그대로 공유함. "내 코드를 리뷰받는 쪽"과 "남 코드를 리뷰하는 쪽" 양방향에서 같은 원장이 자라남

6. 웹뷰 브릿지 계약 OS : 앱↔웹 브릿지 인터페이스 변경 감지 > 양쪽 정의 대조 > 불일치·미구현 핸들러 검출 > (인간) 확인 > 계약 문서 갱신
   - 신호 : 계약 대조 결과 (있다/없다로 딱 떨어짐)
   - 강점 : 타입 시스템이 못 잡는 런타임 경계를 다룸. 실무 밀착도가 가장 높음
   - 약점 : 주제가 너무 특수해서 조별 리뷰에서 남들이 이해하기 어려울 수 있음

7. 성능 예산 OS : 변경분 투입 > 번들 사이즈·주요 지표 측정 > 기준선과 비교 > 예산 초과 시 원인 청크 지목 > (인간) 허용/수정 결정 > 통과하면 기준선 갱신
   - 신호 : 숫자. 셋 중 가장 반박 불가능한 신호
   - 강점 : 루프와 기준선 갱신 구조가 강의 예시의 "시각 회귀"와 같아서 설계가 쉬움
   - 약점 : 바로 그 이유로 **강의에서 이미 보여준 예시와 구조가 겹침**. 차별점을 따로 만들어야 함

8. 릴리즈 전 회귀 OS : 배포 대상 변경분 투입 > 자체 QA 체크리스트 자동 생성 > 브라우저로 항목별 실행 > 스크린샷 기준 비교 > 항목별 PASS/FAIL > (인간) 기준 갱신 승인
   - 신호 : 체크리스트 항목별 판정 + 스크린샷 diff
   - 약점 : 온보딩 문서의 "시각 회귀" 예시와 정면으로 겹침. 2기 수강생이 이미 만든 것이라 굳이 같은 걸 만들 이유가 약함
