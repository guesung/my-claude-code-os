# A. 버그 픽스 OS

## 1. 한 줄 정의

이슈를 받으면 AI가 원인 가설과 재현 환경을 먼저 만들고, **사람이 재현을 눈으로 확인한 뒤에만** 수정으로 넘어간다.
수정이 끝나면 원인·해결·재현법이 문서와 슬랙 초안으로 자동 산출된다.

## 2. 왜 이 주제인가 / 왜 채택하지 않았나

이 OS의 최대 강점은 **판정 기준이 세상에서 제일 깨끗하다**는 것이다.

```
수정 전: 재현 절차 실행 → 실패해야 함 (버그가 살아있음을 증명)
수정 후: 같은 절차 실행 → 성공해야 함
```

이 두 줄이 곧 자동 피드백 신호다. 강의 예시의 "스펙·테스트 주도" OS가 실패 테스트를 먼저 쓰는 것과 정확히 같은 구조인데,
버그 픽스는 **그 실패 테스트를 인위적으로 만들 필요 없이 현실이 공급해준다**는 점에서 오히려 자연스럽다.

탈락 사유는 주제의 질이 아니라 **재료 수급**이다.
4주 동안 매주 3시간 실습과 조별 리뷰에서 보여줄 버그가 그때그때 있다는 보장이 없다.
"이번 주엔 버그가 안 나왔습니다"가 되면 실습 시간이 통째로 빈다.

## 3. 골격

```
[사람]  이슈 링크 투입              재현 확인 ✋        수정 승인 → 이슈/슬랙 공유
          │                          ↑ │                  ↑
          ▼                          │ ▼                  │
[AI]   원인 가설 ──→ 재현 환경 구성 ──┘ 수정 ──→ 재현 절차 재실행 ──→ 원인·해결 문서화
                                          ↑              │
                                          └──── ↻ ───────┘
                                            (재현이 여전히 실패하면)
```

사람의 개입 지점이 딱 두 곳이고 둘 다 이유가 분명하다.

- **재현 확인**: AI가 "재현했습니다"라고 말하는 것과 실제로 재현된 것은 다르다. 여기서 틀리면 이후 전부가 헛수고다.
- **수정 승인**: 원인을 잘못 짚고 증상만 덮는 수정을 걸러내는 자리.

## 4. 구성 요소

**재현 원장** — 이 OS의 심장. 버그 하나당 한 항목.

```
- id: B-014
  증상: 특정 조건에서 모달이 두 번 열림
  재현: 1) ... 2) ... 3) ...
  원인: (사람 확인 후 확정)
  회귀 테스트: 남겼는가 / 남기지 않았다면 그 이유
```

핵심은 **"회귀 테스트를 남겼는가"** 칸이다. 이게 없으면 버그 픽스 OS는 그냥 빠른 삽질 반복기가 된다.
채택안의 리뷰 원장과 같은 사상 — 한 번 겪은 실패는 다음 사이클의 자동 검증 기준이 되어야 한다.

**역할 분리**: 원인 분석자 / 수정자를 나눈다. 자기가 세운 가설을 자기가 검증하면 가설에 코드를 끼워맞춘다.

## 5. 4주 로드맵 (단독으로 갈 경우)

| 주차 | 얹을 것 | 사람 개입 |
|---|---|---|
| 1 | 이슈 → 원인 가설 + 재현 절차 산출 스킬 | 재현 확인, 매 단계 호출 |
| 2 | 분석자 / 수정자 분리. 재현 원장 v0 | 가설 승인 |
| 3 | 재현 재실행 루프 (상한 3회). 회귀 테스트 강제 | 재현 확인 + 최종 승인 |
| 4 | 원인·해결 문서 + 슬랙 초안 자동 산출. 재발 채점 | 재현 확인만 |

## 6. 채택안과의 접속점

채택안의 **리뷰 원장·리뷰어·수정 루프를 그대로 쓰고 앞단만 "설계서" → "이슈 + 재현"으로 교체**하면 된다.
3주차에 이 진입점을 붙이면 "하나의 골격이 두 워크플로를 태운다"는 걸 조별 리뷰에서 보여줄 수 있다.

# B. 문의 답변 OS

## 1. 한 줄 정의

문의를 받으면 AI가 코드베이스에서 근거를 찾아 답변 초안을 만들고, **모든 문장에 근거 코드 위치를 달게 강제**한다.
사람은 근거의 타당성만 검토하고 슬랙으로 내보낸다.

## 2. 왜 이 주제인가 / 왜 채택하지 않았나

빈도와 효능감은 셋 중 제일 높다. 문의는 매주 온다.
문제는 **"답변이 맞았는가"를 자동으로 채점할 방법이 없다**는 것이다.
정답이 없으니 루프가 돌지 않고, 매 사이클이 사람 컨펌 한 번으로 끝나 4주차의 하네스·평가 개념을 얹을 자리가 없다.

**다만 이 한계를 우회하는 설계가 하나 있다.**
답변의 정확성 대신 **근거(citation)의 검증 가능성**을 신호로 삼는 것이다.

```
답변의 각 주장 → 반드시 file:line 을 달아야 함
        ↓
검증자: 그 위치에 실제로 그 코드가 있는가?  ← 이건 자동 판정된다
        ↓
근거 없는 문장 = 환각 후보 → 답변에서 제거하거나 "확인 필요"로 강등
```

"맞았는가"는 못 채점해도 **"지어냈는가"는 채점된다**. 이 각도로 재설계하면 루프가 성립한다.
그럼에도 채택하지 않은 이유는, 이렇게 만들어도 4주를 채울 층이 2~3주 분량이기 때문이다.
1주차 과제나 채택안의 곁가지로는 훌륭하다.

## 3. 골격

```
[사람]  문의 투입                            근거 검토 → 슬랙 발송
          │                                      ↑
          ▼                                      │
[AI]   코드 탐색 ──→ 답변 초안(근거 필수) ──→ 근거 검증 ──→ 통과분만 남김
                          ↑                      │
                          └────── ↻ ─────────────┘
                            (근거 없는 문장이 남아있으면)
```

## 4. 구성 요소

**답변 원장** — 나간 답변과 그 근거를 남긴다. 같은 문의가 반복될 때 재탐색 없이 재사용하기 위함이며,
나중에 "그때 그렇게 답했는데 왜 그랬죠"에 답할 수 있게 한다.

**금지 규칙** — 근거 없는 단정, 코드에 없는 동작에 대한 추측, "아마 ~일 것"류의 표현.
이 세 가지를 검증자가 기계적으로 잡아낸다.

## 5. 위치 제안

단독 4주 주제로는 얇다. 대신 **채택안의 1주차 워밍업**이나 **별도 스킬**로 만들어두고,
근거 검증 아이디어(위 2절)만 채택안의 리뷰어 설계에 흡수하는 편이 낫다 —
"리뷰어가 지적할 때 반드시 원장 항목 id를 인용하게 한다"는 형태로 그대로 옮겨진다.
